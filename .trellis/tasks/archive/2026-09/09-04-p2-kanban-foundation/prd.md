# P2 Kanban 基础能力

## Goal

在现有项目容器之上提供管理员可用的轻量 Kanban 视图，使已归属项目的 Feedback 与 WorkTask 能按可理解的工作状态集中查看并进行受控状态调整，同时保持两类来源的数据模型、权限和语义独立。

## 已确认背景

- P2 项目基础能力已经落地：`project`、`project_milestone`、`project_item` 三张增量表，单条来源唯一项目归属，项目详情按 Feedback/WorkTask 分开显示。
- Feedback 当前状态为 `new`、`reviewed`、`resolved`、`notplanned`；WorkTask 当前状态为 `new`、`scheduled`、`in_progress`、`completed`、`cancelled`。两者状态集合和业务含义不完全相同。
- 管理员现有项目详情 API 返回安全来源摘要，现有状态更新 API 分别服务于 Feedback 和 WorkTask；未引入前端框架、ORM、迁移 runner 或实时协作基础设施。
- 产品边界继续保持：KyanetAccount 联动暂停；Feedback 与 WorkTask 不合并；AI、通知不自动修改工作项；当前目标是个人使用、低维护成本和小范围增量。
- 视觉延续现有冷色、直角、亮暗主题和窄屏可访问性规范。

## 本任务范围

1. 在管理员项目模块提供 Kanban 入口/视图，展示当前项目已归属的工作项。
2. 工作项卡片至少显示来源类型、标题、状态和必要的现有摘要；不得显示来源正文、联系方式、管理员备注或内部密钥。
3. 支持通过明确的管理员操作调整工作项状态，并在成功后刷新项目数据；失败时保留用户当前界面状态并给出可理解的错误提示。
4. 保持项目归属、里程碑、公开投影和现有独立 Feedback/WorkTask 管理流程兼容；归档项目不可执行写操作。
5. 状态变更写入现有管理员审计，沿用现有会话、同源、JSON、限流和输入校验边界。
6. 不在本任务新增子任务、依赖、拖拽排序、实时协作、甘特图、批量跨项目操作或用户侧 Kanban。
7. Kanban 保存状态时同步更新项目 `updatedAt`，使项目进展变化反映到管理员项目列表及已开启的公开更新时间。

## 约束与风险

- 必须先确定 Kanban 的列语义。直接把 Feedback 与 WorkTask 映射到一组统一列可能丢失原有状态含义；完全合并两类来源则违反已确认的产品边界。
- 需要保持 SQLite/MySQL/PostgreSQL 三数据库等价，并兼容现有项目表数据，不改变原始 Feedback/WorkTask 状态值。
- 项目状态时间的同步更新会改变项目列表排序及公开更新时间；这是本任务的明确产品行为，不扩展为来源绑定/解绑的全面时间重算。

## 初步验收方向

- [ ] 管理员可从项目详情进入 Kanban，并看到该项目的全部有效工作项。
- [ ] Kanban 的列和卡片信息符合最终确认的来源/状态语义，Feedback 与 WorkTask 仍可区分。
- [ ] 合法状态调整仅更新对应来源记录，项目归属和里程碑关联保持不变；非法状态、归档项目和未授权请求被拒绝。
- [ ] 项目范围状态接口拒绝不属于当前项目的来源；成功状态调整同步更新项目 `updatedAt`，不改变里程碑完成度计算规则。
- [ ] 成功/失败状态调整均有可观察的 UI 结果和脱敏审计记录。
- [ ] API、数据库 schema、前端模型和文档同步；自动回归、语法检查、`git diff --check` 与 Trellis 校验通过。

## 已确认的产品决策

1. Kanban 使用两条来源泳道：Feedback 和 WorkTask 各自使用原生状态列，不做跨来源状态映射。
2. 首版不增加手动排序字段；各状态列沿用 `updatedAt DESC, id DESC` 的确定性排序，卡片移动只改变来源状态。
3. 卡片状态调整采用原生状态下拉框和明确保存操作，复用对应来源的现有状态更新语义，不依赖拖拽。
4. Kanban 作为项目详情的独立视图，与现有关系视图并存；关系视图继续负责绑定、解绑和里程碑调整。
5. Kanban 首版仅管理员可见；公共项目列表/详情继续不返回工作项或 Kanban 数据。
6. 后端新增项目范围状态接口；服务端校验项目活跃状态、来源归属和来源专属状态集合，复用现有来源状态更新与管理员审计，不新增数据库字段。
7. 技术实现优先复用现有项目详情安全 DTO：前端按来源类型和原生状态分组，后端不重复建设独立 Kanban 查询接口。
8. Kanban 状态保存同步更新项目 `updatedAt`；不改变现有里程碑驱动的自动完成度。

## 当前无阻塞产品问题

状态列、排序、交互、视图共存方式、公共范围、项目范围状态接口和读取 DTO 均已确认；剩余实现细节在设计工件中记录，不改变上述产品边界。

## 规划工件要求

这是跨数据库、API、管理员 UI 和审计的复杂任务。需求收敛后必须补充 `design.md` 与 `implement.md`，再执行 `task.py start`；当前阶段不得修改产品代码。
